# hermes-hq — Technical Knowledge

## Architecture (decided 2026-08-29)
- **One Python service** (`backend` package, FastAPI; console script `hermes-hq`) that: contains the engine (`core/` = moved `wm_store`/`wm_dispatch`/`wm_run_agent`), runs the dispatcher as an in-process background loop (no Hermes cron), exposes REST (+ SSE for chat streaming; one WebSocket, the browser terminal), and serves the built React UI from `backend/static/`.
- **Frontend**: React 19 + Vite + Tailwind 4. Desktop top bar (glass, bordered): **Overview · Projects · Tasks · Agents · Chat**; right side **Tools** menu (Files · Terminal · Memory · Skills · MCP · Schedules), theme picker, bell, LIVE/PAUSED dot, SYSTEM. **Phones (<640 px, decided 2026-08-30)**: floating pill tab bar in the top nav's style (`TabBar.tsx`: Overview · Tasks · Chat · **Inbox** (unread badge) · More — Projects and Agents live under More (owner, 2026-08-30), safe-area aware, reserved height `--hq-tabbar`), top row = logo · LIVE + slots only (no bell on phones); `/inbox` (`pages/Inbox.tsx`) = the notification list + alert preferences; Agents, Tools, System, Appearance and Sign out live on `/more` (`pages/More.tsx`). Menus/sheets use the opaque `.hq-menu` surface; all form fields are ≥16 px on phones (iOS focus zoom). Reviews live inside Tasks + Task detail; Activity inside Overview feed + Project detail. (Supersedes the 7-tab IA in `hermes-work-manager/design/IA_FLOWS.md`; decided 2026-08-29.)
- **Theming**: all colors are `--hq-*` CSS vars per `[data-theme]` in `frontend/src/index.css`, exposed to Tailwind via `@theme inline`. Six fixed themes, no OS-follow: violet (default, WM tokens), nous, nous-light (only light theme, from workspace `claude-nous-light`), bronze, slate, hermes (palettes from hermes-workspace `styles.css`). Pref in `localStorage['hq-theme']`; `?theme=<id>` overrides (used for screenshots).
- **Fonts**: only Inter + JetBrains Mono bundled (`frontend/public/fonts`, no CDN, no `@fontsource`). One font choice: JetBrains Mono (default, everywhere), Inter, System Sans/Serif/Mono. Pref in `localStorage['hq-fonts']`; `?font=<id>` overrides. Why: the app renders on each viewer's device, so only bundled fonts look identical; owner wants JetBrains.
- **Shell style**: navbar anatomy from WM v0.9 (full-width glass bar, icon tile + `HERMES // HQ` wordmark + version pill, bordered pill-group nav, sysbar with TOOLS, appearance ◐, pulsing LIVE dot, clock, SYSTEM pill); `glass`/`glass-strong` card utilities; orb + dot-grid body background.
- **Data**: SQLite at `$HERMES_HOME/hermes-hq/hq.db`. One-time importer for legacy `/opt/data/work-manager/wm.db`.
- **Agents**: Hermes profiles, managed only via the `hermes profile` CLI. Roster templates ship in repo `agents/<name>/{agent.yaml,SOUL.md,skills/<name>-specialist/}` (extracted from the live profiles by `scripts/extract_agent_templates.py`; `agents/orchestrator` is an overlay for the default profile's SOUL). Add-agent flow (`backend/agents.py`): pick template → real `hermes profile create --no-alias --description` → layer SOUL + skill; fallback `ask-orchestrator` files a task. Never a custom profile-copy script.
- **Model/provider config** stays in Hermes; hermes-hq stores no API keys.
- **Ports**: hermes-hq default :9010 (legacy WM dashboard stays on :9009).
- **Install**: single command (`curl … | bash` or `pipx install hermes-hq && hermes-hq serve`) on a box with `hermes` on PATH.

## Status model
Engine keeps its precise state machine (`planned, waiting_approval, ready, running, needs_review, rework, blocked, failed, stalled, done, manual`; goals `draft/planning/planned/released`). UI shows 5 human states + reason line:
- **Backlog** = planned/draft
- **Queued** = ready, or dependency-gated (reason "waiting on #N")
- **Working** = running; `needs_review` shown as "Working · reviewer checking" (review is auto-dispatched to reviewer agent — verified `wm_store.py:1699`, `wm_dispatch.py:264`)
- **Needs you** = owner approval, blocked, failed, stalled — each with the one unblocking action
- **Done** = done, manual/archived — but `manual` carries `human.label = "Handed over"` (2026-09-01): the chip shows that label while grouping/order stay in the done bucket; `classify()` emits `label` only for manual, `status.ts` mirrors it, `StatusBadge` prefers `human.label`. EXCEPT gated manual (below): `owner_approval=1 && status=manual` classifies as **needsyou** with label "Awaiting approval" / reason "awaiting your approval". A stranded orchestrator `Plan goal #N` task under a `planned` goal instead exposes `approve_plan` / "plan awaiting your approval".

## Approval gate (2026-09-01, `intent/ApprovalGatePlan.md`)
- `tasks.owner_approval` (INTEGER, default 0; additive migration): completions that would reach `done` land on `manual` instead — after the agent review resolves when `review_policy` is required/optional (gate in `review_verdict` approved path, detail "review approved — awaiting owner approval", NO dependent promotion), directly in `record_completion` when policy is none. Genuine manual work uses close-owner (= audited done, promotes dependents) or feedback (→ rework). Plan approval is separate: `approve_plan` requires a manual orchestrator planning task and a still-planned goal, durably releases the goal, closes that planning row, then promotes its eligible dependents; API `/api/task/{id}/approve-plan`. Approval buttons are consequence-named (#140, 2026-09-02): "Approve plan → start build (#N)" when dependents exist (else "→ start coding"), gated close-owner reads "Approve → release (#N)" with dependents / "Approve → done" terminal; the Feedback modal warns (non-blocking) when the text looks like an approval. Stale/non-plan approvals are refused.
- Completion contract now has FOUR verdicts: `done|blocked|failed|manual`. `manual` = agent-initiated hand-over (run finishes `done`, blocker = what the agent needs decided) and it SETS `owner_approval=1` in the same transaction — the continuation stays gated until the owner untoggles. Routing (#143, 2026-09-02): on `review_policy=required` a manual verdict lands on `needs_review` first (review auto-created transactionally) and reaches `manual` only after an approved review — it can no longer skip the reviewer; `optional`/`none` stay direct-to-manual. Review runs keep 3 verdicts (`manual` from a review run = contract error → failed; guard in `wm_run_agent._finalize`). Work brief renders an "OWNER APPROVAL GATE" line on gated tasks; review brief text untouched.
- **Phase-gate workflow (2026-09-02, `docs/workflow.md` is the user-facing spec)**: work is modeled as LINKED TASKS, not phases-in-one-task. `wm task create ... --phased` (CLI + UI toggle) creates "<title> — plan" (given assignee, `review_policy none`, `owner_approval 1`) + "<title> — build" (`is_code 1`, `review_policy required`, owner flag as supplied) with build depending on plan; owner-closing the plan promotes the build (`close_by_owner` dependent promotion). Intake is interview-FIRST: the orchestrator's `orchestrator-intake` skill (deployed `/opt/data/skills/`) defers to the verbatim Matt Pocock `grilling` skill — frontier rounds of numbered questions with recommended answers, facts looked up never asked, create only after the owner confirms; it also enforces the proof rule (owner-only proof — deploy, live Lighthouse — becomes a separate owner-gated INTEGRATE/VERIFY task, never an agent DoD clause).
- **Dispatch safeguard (2026-09-03, `intent/OwnerGatedDispatchPlan.md`, commit `6a0d02f`)**: `owner_approval=1` is now enforced in the dispatch paths themselves — `claim_task` and `next_ready_tasks` require `owner_approval=0`, `release_goal` and `_mark_ready_if_deps_done` (hence all dependency/parent promotion) leave gated tasks in `waiting_approval`. Clearing the gate via `edit_task(owner_approval=False)` IS the approval event: it auto-runs `_mark_ready_if_deps_done`, so an approved task becomes `ready` on its own when the goal is released and deps are done. Closed 2026-09-04 (`16d349c`, `intent/GatedReadyFixPlan.md`): `mark_ready`/`retry_task` now REFUSE gated tasks with instructive errors (409 via API) — gated-ready is impossible to create (legacy rows stay protected by the claim predicate and dispatch once the gate clears); `classify()` surfaces gated `waiting_approval`/`ready`/`rework` as needsyou "Awaiting approval" (deps kept in reason; unreleased goal outranks the gate); TaskDetail shows "Approve → queue" on those statuses, wired to the audited edit path. Approval remains `edit_task(owner_approval=False)` — never mark-ready.
- Project create can optionally seed a KIS memory skeleton (`backend/writes.py` + form toggle, 2026-09-03, `a84d1a9`).
- `→ manual` transitions already raise `needs_you` notifications (`NOTIFY_NEEDS_YOU` has contained `manual` since before the gate) — no new notification code.
- Toggle: `wm task create/edit --owner-approval`, `POST /api/task/{id}/edit {owner_approval}` (same gates as description edits: refused running/done), TaskDetail gate chip button (audited).
- Readable results: `backend/files.resolve_artifact(abs_path)` maps a result_path into `{root, rel, kind, exists}` via the files-API containment (deepest project primary_path wins, else projects root); task detail attaches `artifacts`; TaskDetail renders text/markdown inline (chat `Markdown` component; `.md` rendered, others `<pre>`, 1 MB cap honoured via `too_large`), images inline via `/api/files/raw`, plus an "Open in Files" deep link (`/files?root&path`). Paths outside every root stay plain text.

Owner overrides (2026-08-31): `manual` is the owner's hand-over state — "Take over" (any open status) then "Close as done" (`close_by_owner`: manual-only, records the done transition so `wm check` passes, waives open reviews, promotes dependents; CLI `wm task close <id> --by-owner -c`, API `POST /api/task/{id}/close-owner`). Owner feedback also works FROM `manual` (→ rework, words threaded into the next brief). Audited task edit: `edit_task` (description/DoD only; refused while `running` — brief already rendered at claim — and on `done`; `task_edited` activity keeps the old values; `wm task edit --description/--dod`, `POST /api/task/{id}/edit`, pencil-edit on TaskDetail; `render_brief` reads the task row at claim time so edits land in the next brief). Feedback from `ready` stays refused by design — edit is the tool there. Dep edges: `wm task depend` / `wm task undepend` (undepend re-checks release eligibility; repoint = undepend+depend). `wm goal delete` removes a DRAFT goal nothing references (activity rows keep history but detach their FK); tasks/runs are NEVER deleted (session-marker id reuse) — goals are the one sanctioned delete.

## Auth + unblock rules (decided 2026-08-29)
Single password (`HERMES_HQ_PASSWORD`, else generated → serve log + `$HERMES_HQ_HOME/password`), cookie session, CSRF header on mutating requests, everything under `/api/*` behind login. Plain HTTP on LAN/Tailscale is accepted for a single owner; HTTPS is a reverse-proxy concern. Unblock semantics: `blocked` → primary action is owner feedback (→ `rework`, comment threaded into next brief); `failed`/`stalled` → `retry_task` (→ `ready`); `mark_manual` takes a task out of the queue. Writes only ever call `core.wm_store` functions; engine `ValueError` → HTTP 409 with the engine's message. `OWNER_FEEDBACK_SOURCE_STATUSES` includes blocked/failed/stalled, so a reply re-queues a stuck task as rework; the feedback is injected into the next brief even though the dispatcher claims (→ running) before rendering it.

## Engine rules carried over (non-negotiable)
- Every task belongs to a project with a valid `primary_path` (default `/opt/data/projects/<slug>`, root configurable).
- One persistent Hermes session per task run; session id must be deterministic, never "newest session".

## Frontend build gotchas (learned 2026-08-29)
- Vite/Tailwind CSS minify keeps only the LAST of a prefixed/unprefixed pair: write `-webkit-backdrop-filter` before `backdrop-filter`, or Chrome (which ignores the `-webkit-` form) gets no blur.
- `overflow-x: hidden` on `html, body` makes body a scroll container and silently kills `position: sticky`; use `overflow-x: clip`.
- `npx tsc ... | tail` masks the exit code — chain with `&&` and no pipe when a failure must stop a commit.
- `hermes-hq` serves `index.html` with `Cache-Control: no-cache`; hashed assets are immutable, so a plain reload picks up new builds.

## Browser terminal (Group 6-1, 2026-08-30)
- `backend/terminal.py`: `WS /api/terminal/ws?session=&cols=&rows=` relays a real PTY (`pty.fork` → `bash -i`, `TERM=xterm-256color`). The shell runs as the **`hermes` user** (`HERMES_HQ_TERMINAL_USER`, uid/gid 10000): when `serve` runs as root the child drops privileges before `execve` and aborts if that fails; `HOME=/opt/data/home` (`HERMES_HQ_TERMINAL_HOME`), falling back to the passwd home when the dropped uid cannot enter it. `hermes` can read `/opt/data` and `config.yaml` but not root-owned trees (hq repo, `/opt/data/projects/*`) — accepted.
