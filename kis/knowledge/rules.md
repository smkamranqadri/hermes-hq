# hermes-hq — Working Rules
- Don't copy features from the three source projects without asking; `knowledge/project.md` lineage table is the allow-list.
- Real data only in the UI; empty/error states are honest, never faked.
- Owner-dependent questions are held, never guessed by agents.
- Prove work with real command output before marking done.
- Communication: short, lead with the decision, label choices A/B/C.
- Every list/detail page shows a content-shaped skeleton while loading and a spinner on busy buttons (`Skeleton`, `Btn busy`); applies to all future pages.
- Every new/changed page is checked at 390×844 with mobile emulation before done: tab bar clearance, safe areas, 16 px fields, `scrollWidth` 390 (missing `min-w-0` is the usual overflow cause).
- Owner changes to requirements must be edited into the task **description/DoD** — mid-run guidance (answer files, chat) does not bind the reviewer (learned 2026-09-02, task #138).
- **A code run that leaves its worktree dirty has not finished** (2026-09-07, engine-enforced in `record_completion`): `git status --porcelain` must be clean when a run reports done, or the run fails and the task returns to `rework` naming the uncommitted paths — bounded by `MAX_REWORK_CYCLES` so it parks on the owner's desk instead of re-dispatching forever. Gate on a DIRTY TREE only (a clean tree with no commits is a legitimate investigate/verify run), and the check FAILS OPEN on every error path. **Scoped to `is_code` runs** (owner decision 2026-09-07, task #205): a non-code run gets no worktree — `wm_dispatch` hands it the project's `primary_path`, the SHARED checkout — and has no branch to commit to, so gating it failed runs for dirt anyone else had left there (librarian run 465 was failed for an untracked harness directory it never touched, and its task began cycling toward the cap). Agents commit on their run branch and never merge to main; integration is a separate task. **Why it is in the engine and not just the brief:** 13 of 31 worktrees held work from runs marked done because nothing enforced it — a rule that lives only in a prompt eventually gets skipped.
- **A proposal kind whose effect cannot be undone is owner-eyes by construction, never by taste** (2026-09-08, Phase 3 wave 0): before adding a kind, look for its delete path — route, CLI verb, store function. `append_entry` has none anywhere (`note_entries` is append-only), so it joined `contradiction`/`new_task` in `OWNER_EYES_KINDS` and can never be bulk-approved. The same check decides the *default*: where an agent supplies content the owner cannot later remove, default to the owner's own words **verbatim** — `note_entries` has no author column, so a librarian paraphrase would be indistinguishable from the owner's writing forever after.
- **A passing proof can be passing for the wrong reason — check what the fixture handed it** (2026-09-08): 2b-i's contradiction proposal verified green while the librarian had no way to *find* a sibling note, because the planted pair both sat in the inbox where their ids were already visible. The feature shipped with an undiscoverable step and the shipped skill instructed "search first" for eleven days with no search command in existence. When a proof depends on an agent discovering something, verify the discovery path itself, not just the outcome.
- **The owner is the taxonomy authority, agents are not** (2b-ii): owner/import note writes auto-register their tags in `note_tag_taxonomy`; agent proposals may only use registered tags, and coinage must be declared (`new_tags` / `--new-tags`) and is registered *only* when the owner approves. Apply the same shape to any future agent-authored vocabulary (areas, note types).
- **Adding an agent profile includes refreshing the existing specialists' SOUL/MEMORY rosters in the same change** (learned 2026-09-06: the six older specialists predated the Librarian and none of their rosters listed it).
- **Anything an agent proposes or does that awaits the owner must be visible on EVERY surface the owner naturally lands on** — the list row, the detail page, AND the dedicated queue; a queue alone is not enough. (Learned 2026-09-06: three consecutive owner confusions over one librarian proposal that only the Review queue showed — fixed with the inbox `pending_proposal_id` chip and the note-page ProposalBanner. Apply the same test to future proposal kinds, lint findings, and run questions.)

- **The owner's answer file is append-only and the LAST line is authoritative** (2026-09-07, now in `_ask_owner_lines` so every brief carries it): agents must re-read the WHOLE file and act on the last line, because earlier lines may be stray taps or a choice the owner then changed, and a correction is always appended below what it corrects. Learned the hard way — run 466 quoted an earlier line and recorded an answer the owner never chose.
- **A decision the owner makes by tapping must never be sent by the tap itself.** Selecting is not sending: show the selection, require an explicit send, and leave a receipt saying what was delivered. (2026-09-07: single-choice option chips fired the POST on tap with no visible selection, so exploratory taps answered agents irreversibly — one run received `A,A,B,A,B,A` in 18 seconds.) Applies to any future control that commits an owner decision to an agent.
- **State never caches what the live DB already knows** — not counters (unread notifications, queue depths, run counts) and not task STATUS. Name the item that needs a decision; let the board be the authority on where it stands. Anything else is wrong within hours and reads as work that still exists. Learned three times in two days (2026-09-07/08): "18 unread notifications" survived a sync after the owner had cleared them; then "all read" went stale at 29; then State kept #189/#198 on the owner's desk after he had closed them. The pattern is always the same — State restates rows the owner then changes by using the app.

- **A note has exactly ONE area, and an ambiguous filing is never `routine`** (owner decision 2026-09-08 — he chose per-note judgment over a rule, and over multi-area membership): cross-cutting belonging is carried by tags and the project link, never by a second area. But WHICH area is the owner's call, so the librarian picks the best one, files the other dimension as a tag or project, and names in its summary the two areas the note sat between. The failure mode being prevented is not picking wrong — it is picking **silently**. The cost is accepted: across ~670 incoming notes this sends MORE proposals to the owner's desk, not fewer.
- **An area is retired by ARCHIVING it, never deleted, and only at zero live notes** (2026-09-08, mirroring the archive-only note lifecycle): `list_areas` and `notes_tree` both filter `archived=0`, so one flip hides an area from every filing surface at once — which is what makes retiring cheap and also what makes it dangerous. `update_area` refuses while any non-archived note (active **or inbox**) is still filed there, or a live sub-area hangs off it, and the refusal names the count so the caller knows what to refile. **The mirror rule is the one that is easy to miss: LABEL resolution must still see retired areas** (`list_areas(archived=True)`, `get_note`'s join, `GET /api/areas?include_archived=1`) or an archived note renders with no home at all and reads as though it was never filed. Filing surfaces take the default; label surfaces pass the flag.
- **An area's description IS its filing rule, and the exclusion is the load-bearing half** (2026-09-08): every area says what belongs there AND names where the excluded thing goes ("Content — what I publish; reading lists live in Reading"). `wm note areas` prints it under every name and the librarian files by it. Without descriptions the agent files by the NAME, which is exactly what the wave-1 review spent its rejections correcting (`docker manager` → AI Workflow, corrected to DevOps; `desk pet` → Home, corrected to DIY). An area that cannot get a one-sentence description distinguishing it from its neighbours is a taxonomy question for the owner, not a boundary for the agent to invent.
- **An optional nullable field cannot distinguish "absent" from "explicit null" — send only the fields the caller set** (2026-09-08, caught by a test before it shipped): a pydantic `description: str | None = None` forwarded unconditionally wipes the stored description on every PATCH that only meant to rename. `model_fields_set` on the request and an `_UNSET` sentinel in the store are the two halves of the same fix — and keeping both means an explicit `{"description": null}` can still deliberately clear the field. Applies to every future PATCH model.

- **A worklist must never let a page limit read as "nothing to do."** (2026-09-10, cost a full stall.) A triaged note keeps `status='inbox'` until the owner decides, so already-proposed rows accumulate in the inbox; they were the newest, the list sorted newest-first, and `wm note inbox` capped at 100 — so 101 pending rows filled every slot and four consecutive librarian runs reported "0 untriaged" while **148 notes waited**. Each successful run made it worse by pushing more pending rows to the top. Two rules fall out: a worklist EXCLUDES what is already handled, and it prints the **true outstanding count computed independently of the page** (`count_untriaged_inbox`), so a limit can never masquerade as an empty queue. And when a brief tells an agent to work oldest-first, the command must hand it the oldest — ours handed it the newest, so the two could never meet.
- **A failed run must name its own cause, and the log scanner must be tested against REAL logs.** (2026-09-10.) Two runs failed as the bare contract message "missing completion file" while the truth sat in the log: one was a provider outage ("API call failed after 3 retries: Hermes can't reach the model provider"), the other the agent's own admission at exit code 0 ("I couldn't complete the required final completion-file write"). Every tier-1 pattern demanded `api error`/`connection error` ADJACENCY, so "call failed" slipped past. **Testing the fix against invented sample strings passed while the real log still returned None** — agents write prose with **U+2019 smart quotes**, and `could not` (spaced) is as common as `couldn't`. Pin log-scanner tests to the actual production log text, verbatim.
- **`routine` is the classification that skips the owner's eye, so it earns the most scrutiny, not the least.** (2026-09-10.) Of 26 proposals the librarian marked `routine` — the bucket built for bulk approval — **two were wrong**: one archived a list of names-with-meanings (`Name A and its meaning`, `Name B and its meaning` — a names list) as "no context establishing… family", and one justified archiving by calling a 2,612-char note "a one-line duplicate" of a 1,646-char note it could not fit inside. Both outcomes were non-destructive, but that is a **1-in-13 fault rate in the bucket designed to be waved through**. Sample `routine` before bulk-approving it; the classification says the agent was confident, not that it was right.
- **A shadow copy needs the same filing as its live twin.** (2026-09-10.) Imports that keep an `Archive/` copy beside a live one filed only the live one, so `Teammate` was findable in Work while the archived `Teammate` sat area-less and Work's archive showed none of the feedback history. When two notes are linked as superseded/current, the archived one inherits the live one's area — and where no link exists, **tag dominance is a second independent signal** that agreed with the link on nearly every case here (`feedback` 12/12 Work, `server-setup` 7/7 DevOps, `docker` 13/13 DevOps). Beware the false friend: a same-TITLE match is not a twin — `notes` (the 6,022-char old-hermes export) and `Notes` (an 82-char UI complaint) share nothing but a name.

- **An agent's summary is a PROMISE about its payload, not a description of its reasoning** — the owner approves from the summary, so anything it asserts must be checkable against what the payload does. Three rejections of this exact shape (2026-09-09/10): one summary described a completely different note (`#274` said "2021 HacktoberFest meetup" for a product-owner job description), several asserted years the notes never carried (`created_at` is the IMPORT stamp, never evidence of content age), and one named Home and Reading for eight split parts that shipped with **no `area_id` at all**. The prose is consistently more confident than the payload; check the payload, never the prose.
- **An agent under correction fixes what it was just told and quietly regresses what it was told last time.** (2026-09-10, note #770 over three rounds.) Round 1 dropped 192 words including a real GitHub link; round 2 fixed the content and shipped every part unfiled; round 3 fixed the filing and lost a URL again. A rejection must therefore re-state what the previous round got RIGHT, not only the new fault — and the acceptance rule belongs in the DoD, where a run fails against it, rather than in prose it can drift from.
- **An area with no notes is not an area with no purpose.** (2026-09-10, Home retired then restored.) Home was retired on solid evidence — 0 active notes, its only archived ones a misfiled Work item — but that evidence came from a corpus of three developer-shaped sources that had not yet received the one most likely to fill it. Wave 4's Apple Notes immediately stranded `City Trip Plan`, `Ride Booking` and `Camera` with nowhere to go, and Home took **35 notes** within a day of coming back. Where an empty area names a real part of life, describe it rather than retire it until every source has landed.

- Never assume hermes-hq runs inside the Hermes docker/s6 container (owner, 2026-08-29). Detect the platform (installed service vs. none) and fall back to owning the process; no hardcoded `/run/service`, `s6-svc`, `/opt/data` or container users in code.

- **Multi-slice build cycle (owner-decided 2026-09-08, after the Library polish A–D cost ~1.4 M tokens):** the orchestrator plans in `kis/`, merges and deploys, and builds SMALL slices itself; large slices go to an **Opus** builder subagent in its own worktree (Sonnet builds cost 2–3 review rounds each) and always to a fresh **Opus** reviewer; every builder uses the shared scratch kit `tools/scratch/` (serve/seed/stop + `pw.mjs`, Playwright installed once at `/opt/data/hh-scratch/pw`, `node_modules` symlinked — never `npm ci`/`npm i playwright` per worktree) instead of hand-rolling a scratch server. Full recipe: `tools/scratch/README.md`. Two slices in parallel only when they touch different files. After a backend restart the owner's phone keeps the old bundle until the Home Screen app is closed and reopened — say so in every deploy report (auto-reload declined).

- **Never run `npm run build` while the backend suite is running.** The build recreates `backend/static/assets`, and any test that mounts the static dir fails with `RuntimeError: Directory '.../backend/static/assets' does not exist`. It has produced a phantom failure twice on 2026-09-10 — once for a builder subagent, once for me — and both times the first instinct was to hunt a regression that did not exist. Re-run the file alone to confirm before believing any failure that names a static path. (2026-09-10.)
- **A default that COPIES text into a second table needs an edit path for the copy, or it becomes permanent.** `new_task` from a note prefilled the task title from the note and embedded it in the description, while `edit_task` could not change a title at all — so a note that later turned out to be sensitive left its title in `tasks` with deletion as the only remedy, and Phase 4's move-to-vault had to REFUSE rather than offer a fix. Fixed 2026-09-10 (title is editable and audited; the description copy is gone). The general rule: before defaulting one record's text from another's, ask what happens when the source turns out to be wrong or sensitive. (2026-09-10.)

- **A path gate must normalise before it decides.** `AuthMiddleware` tested `path.startswith("/api/")` on the raw path, so `//api/system` slipped past it while reaching the same route — and the SPA catch-all, which `os.path.join`ed an attacker-supplied absolute path onto the build dir, then served **any readable file to an unauthenticated request** (the owner's password file and `sessions.json` among them, proven live 2026-09-10). Two rules fall out: normalise (collapse `//`, resolve `.`/`..`) before any allow/deny test, and **never `os.path.join` untrusted input onto a base** — an absolute second argument discards the base. `realpath` and confine instead. (2026-09-10.)
- **A `LIKE ? ESCAPE '\\'` pattern must escape the ESCAPE character first.** Escaping only `%` and `_` leaves `\\` live, and SQLite then takes the next character literally — so a value containing a backslash builds a pattern that does not match its own text. In the vault's title-survival guard this failed **open and silently**: the guard matched nothing, the destructive move was allowed, and the confirm dialog truthfully reported zero affected rows. Any security control built on `LIKE` inherits this. (2026-09-10.)
- **A test client can silently rewrite the thing you are testing.** httpx reads a leading `//` as a **protocol-relative URL** — `client.get("//etc/passwd")` sends host `etc`, path `/passwd`, so a path-traversal test passes without ever sending the path. Pin the parse (`httpx.URL(BASE + probe).path == probe`) or use an absolute URL. The general rule: for any test asserting a defence, **break the defence and watch the test fail** before believing it. Three separate green-but-vacuous tests were caught this way on 2026-09-10. (2026-09-10.)

- **Never `git checkout <file>` to undo a negative-control experiment — it reverts the fix you have not committed yet.** Running controls means deliberately breaking the code to prove a test fails; restoring with `git checkout` restores from HEAD, which silently throws away any uncommitted fix in that file. Copy the file aside first and copy it back. Hit on 2026-09-10: a `git checkout backend/push.py` erased a just-written fix, caught only because the next `git diff --stat` did not list the file. (2026-09-10.)

- **A documented escape hatch that nobody exercises is not an escape hatch.** `wm dispatch` — the manual dispatcher tick, and the documented way to force work through when the loop misbehaves — raised `ModuleNotFoundError` on every invocation for roughly a month (`import wm_dispatch` where the module is `core.wm_dispatch`). Nothing caught it because the live service runs its own dispatcher loop, so the command was never called until it was actually needed, mid-incident. Fixed and pinned by a test 2026-09-10. **The rule: any command documented as a recovery path needs a test that RUNS it** — the moment you need it is the worst moment to discover it was dead. Same reasoning as the librarian-surface guard: a capability nobody exercises decays silently. (2026-09-10.)

- **A test must never write into a path derived from a MODULE's own location.** `tests/backend/conftest.py` clears the engine env overrides and fixtures set `HERMES_HQ_HOME`, which sandboxes everything resolved from `hq_home()` — but **not** `backend.app.STATIC_DIR`, which is `os.path.dirname(backend/app.py) + "/static"` and therefore always the real build directory. On 2026-09-10 a new test wrote a 32-byte fixture `index.html` there and **replaced the owner's live frontend**; the server kept answering 200 and the app served a white page until the next `npm run build`. Before a fixture writes anything, ask what that path resolves to when the env vars are pointed elsewhere — and if it is module-derived, `monkeypatch.setattr` it to a tmp dir. (2026-09-10.)

- **Test the WIRING, not the helper — a test that calls the new function directly proves the function, never that anything uses it.** Three times on 2026-09-10 a negative control passed against deliberately broken code for exactly this reason: the push watermark (gutting `sync_and_push` left the test green), and twice for notification dedupe (the collapse could be deleted from `push_notifications` entirely). Each time the fix was to drive the real entry point — `push.sync_and_push`, `push.push_notifications` against a fake push service — and each time the rewritten test failed immediately against the broken code. **The negative control is the only thing that tells the two apart**, so run it on anything load-bearing: break the feature, watch the test fail, restore. (2026-09-10.)
