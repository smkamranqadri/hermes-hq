# The phase-gate workflow

This is the normal path for a new user with a rough idea. The owner makes the
forward-moving decisions; agents do the work and provide evidence.

## The short version

```text
rough idea
   |
   v
Orchestrator interview in chat
(one question at a time)
   |
   +--> PLAN task / breakdown task
   |       |
   |       v
   |   owner approves the plan
   |       |
   |       v
   +--> BUILD task(s)
           |
           |  isolated code worktree + required Reviewer
           v
       owner accepts the result
           |
           v
       INTEGRATE / VERIFY
       owner-only proof: deploy, live Lighthouse, etc.
           |
           v
          done
```

For a goal-backed new-user flow, the PLAN task is the goal's Orchestrator
breakdown task; its owner approval releases the dependent BUILD task(s). That
is the path shown above. [core/wm_store.py:947-1042, 2637-2689]

The separate CLI convenience flag `--phased` creates two linked tasks in one
action: `<title> — plan` and `<title> — build`. The build depends on the plan.
The plan has no review and is not a code task; the build is a code task and
requires the Reviewer. Both receive the requested assignee, and the build
receives the requested owner-approval setting. [core/wm_store.py:1270-1285]

## A new task: from idea to verified result

### 1. Start with the rough idea

Tell the Orchestrator what you want in chat. It interviews you one question at
a time until the request is clear enough to plan. Do not skip the interview by
trying to write an implementation brief yourself: the purpose of this gate is
to turn an ambiguous idea into an agreed plan and testable task boundary. The
intake skill requires this interview before creating a task or goal, and covers
scope, constraints, DoD, and proof. [agents/orchestrator/skills/orchestrator-intake/SKILL.md:16-22]

For a standalone task, the task pair can be created from the CLI with the
shipped `--phased` flag:

```bash
wm task create <project> "<title>" "<description>" "<definition of done>" \
  --assignee <profile> --phased
```

The CLI also accepts `--goal <id>` and `--owner-approval`. The complete task
parser defines these flags, plus `--is-code` and `--review-policy` for
non-phased tasks. [core/wm_cli.py:891-915]

The HTTP equivalent is `POST /api/tasks` with `phased: true`; its input also
accepts `project`, `title`, `description`, `definition_of_done`, `assignee`,
`goal_id`, and `owner_approval`. The response includes both `id` and
`build_id`. [backend/writes.py:130-177]

Important distinction: `--phased` does not make a standalone plan task use the
goal-specific `Approve plan → ...` action. Its plan starts as `planned` and is
parked; use `wm task mark-ready <plan-id>` when you intentionally want to run
that standalone plan. The plan-specific approval action is for the special
goal breakdown task described in the goal path below. [core/wm_cli.py:399-409]
[core/wm_store.py:1270-1285]

### 2. PLAN: the agent proposes the work

The plan task is the first gate. It is deliberately not dispatched just because
it exists. The owner reads the plan, its proposed tasks, and its evidence
requirements.

When the plan is waiting for the owner, the UI's plan-specific button is:

```text
Approve plan → start build (#<dependent task id>[, ...])
```

If there is no dependent build task, the actual fallback label is
`Approve plan → start coding`. The confirmation text says that approving the
plan releases its dependents. These are the labels generated by the shipped UI,
not aliases. [frontend/src/pages/TaskDetail.tsx:137-152, 184-187]

Approving the plan calls the plan-specific action. It releases the goal, marks
the planning task done, and promotes eligible dependent tasks. The plan action
is only valid for the Orchestrator's `Plan goal #...` task, while its goal is
still `planned` and the task is `manual`. [backend/writes.py:230-234]
[core/wm_store.py:2637-2689]

### 3. BUILD: implementation in its own worktree

After approval, the build is eligible for the dispatcher (immediately if its
dependencies are done, otherwise after they are). The dispatcher launches code
tasks in a dedicated git worktree and branch named `wm/run-<run id>` when the
project is a git working tree. This keeps a run or retry from writing over main
or another run. Non-code tasks stay in the project's primary path. [core/wm_dispatch.py:53-99]

A phased build has `is_code=1` and `review_policy="required"`, so a Reviewer
run is part of the chain. A review run does not advance the task by itself; the
Reviewer verdict does that. [core/wm_store.py:1279-1284]
[core/wm_run_agent.py:329-342]

The agent reports completion using the run contract. The accepted `completed`
values are exactly `done`, `blocked`, `failed`, and `manual`. The agent may
only claim proof it can actually produce in its own task's Definition of Done.
[core/wm_run_agent.py:265-273]

### 4. Owner accepts the result

The owner reviews the agent's summary and artifacts, then chooses one of the two
meaningful decisions:

- Approve/close: accept the work and let the chain continue.
- Feedback: send it back for rework with a written reason.

For a normal owner-approval gate, the shipped button is `Approve → release
(#<dependent task id>[, ...])` when dependents exist, or `Approve → done` when
there are none. Without that gate, the button is `Close as done`. The button
labels and confirmation text are generated in the same UI code. [frontend/src/pages/TaskDetail.tsx:137-152, 186-187]

The CLI equivalents are `wm task close <id> --by-owner` for a task already in
`manual`, and `wm goal release <id>` for approving a planned goal. Owner-close
is intentionally manual-only: the owner must first use `wm mark manual <id>` if
the task is still in the queue. [core/wm_cli.py:956-964]
[core/wm_cli.py:874-877, 763-775]

### 5. Feedback always means redo

Feedback is not an approval in disguise. It ALWAYS means redo: the task becomes
`rework`, the written comment is placed in the next run's brief under owner
feedback, and any open review is closed as `changes_requested`. [core/wm_store.py:2343-2429]

The actual UI labels are `Feedback → rework` and, while already reworking,
`Add feedback`. In the modal the submit button is `Send & rework`, and the UI
warns: `Feedback sends this task BACK for rework — to approve, use the Approve
button.` [frontend/src/pages/TaskDetail.tsx:182-184]
[frontend/src/components/forms.tsx:78-90]

The CLI form is explicit and requires a comment:

```bash
wm task feedback <id> --comment "what to change"
```

[core/wm_cli.py:937-944]

### 6. INTEGRATE / VERIFY: owner-only proof

The agent task ends when the agent has produced the proof available from its
own run: code changes, tests, local checks, artifacts, and a truthful summary.
It must not promise proof that requires the owner's environment or credentials.

Create or use a separate INTEGRATE / VERIFY task for proof only the owner can
produce, such as deploying to the live environment, checking the live URL, or
running live Lighthouse. The owner performs and records that proof, then accepts
that task. This keeps live deployment and live-site evidence out of the agent's
Definition of Done. The work manager supports task descriptions,
`definition_of_done`, artifacts/result paths, owner approval, and explicit
owner-close; it does not silently treat a local agent completion as live proof.
[core/wm_cli.py:351-380]
[core/wm_store.py:2602-2634]

## Goal path: one interview, then a chain of coding tasks

A larger outcome follows the same gates, with one extra decomposition step:

```text
goal (draft)
   |
   | wm goal plan <id>
   v
interview + breakdown / Plan goal #<id> task
   |
   | decomposition agreed
   | wm goal planned <id>
   v
goal (planned) -- owner approves breakdown --> goal (released)
   |
   +--> coding task A: plan -> build -> review -> owner accept
   +--> coding task B: plan -> build -> review -> owner accept
   +--> ...
              |
              v
       owner-only INTEGRATE / VERIFY -> done
```

The CLI goal lifecycle is deliberately explicit:

```bash
wm goal create <project> "<goal title>" [description] [acceptance_criteria]
wm goal plan <goal-id>
# Orchestrator interviews and creates the breakdown
wm goal planned <goal-id>
# owner approves the agreed breakdown
wm goal release <goal-id>
```

A new goal starts as `draft`, so it cannot be released. `wm goal plan` creates a
real Orchestrator decomposition task, moves the goal to `planning`, and parks
the task in the backlog; no agent starts automatically. `wm goal planned` moves
it to `planned`, which is the approval-ready state. `wm goal release` is the
approval gate and changes the goal to `released`; eligible children become
`ready`, while children with unfinished dependencies wait. [core/wm_cli.py:85-114, 118-136, 175-192]
[core/wm_store.py:713-720, 947-1042, 1065-1129]

Once released, each coding task follows the same plan/build/review/owner
acceptance chain described above. A phased task linked to a goal can be created
with `wm task create ... --goal <goal-id> --phased`; the build's dependency on
its plan is created automatically. [core/wm_cli.py:894-915]
[core/wm_store.py:1270-1285]

## Definition of Done rule

An agent task's Definition of Done may contain only proof that the assigned agent
can produce and attach from its run. Examples include tests run in the worktree,
local checks, generated artifacts, and a recorded summary.

Do not put owner-only proof in that list. Deployment, live URL checks, production
smoke tests, live Lighthouse, credentials, and other proof requiring the owner
or a live environment belong in the separate INTEGRATE / VERIFY task. This rule
prevents an agent from claiming `done` while leaving the only real acceptance
step unperformed.

## Status words you may see

The engine uses these precise task statuses: `planned`, `waiting_approval`,
`ready`, `running`, `needs_review`, `rework`, `blocked`, `failed`, `stalled`,
`done`, and `manual`. The UI groups them into human-facing states, but these
engine values are the source of truth. [README.md:16-26]

In particular, `manual` means the task is out of the queue and needs a human
decision when owner approval is set; a plan awaiting approval is shown as
`plan awaiting your approval`. A task that receives feedback moves to `rework`,
not back to approval. [backend/status.py:45-70]
